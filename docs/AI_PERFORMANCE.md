# AI 回答性能基线

当前阶段：测量、提速、流式输出和 M8 最终复测均已完成。M8 的 24 个成功请求首段文字中位数 2.073 秒、P95 3.888 秒，完整回答中位数 7.458 秒、P95 11.441 秒，流式中断为 0。最终线上函数为 v35。

## 测量范围

`campus-ai` 的每个正常返回响应带有 `Server-Timing` 响应头：

| 字段 | 范围 |
| --- | --- |
| auth | 公开凭据校验，包含必要时的数据库回退校验 |
| quota | 配额检查 |
| knowledge | 已发布文档读取、解析与有效期过滤 |
| keyword | 关键词排序 |
| embedding | 问题向量生成（未启用时可能接近零） |
| vector_rpc | 向量查询与解析；没有向量时不执行 |
| model | 上下文构造、模型请求、完整响应解析 |
| unanswered_log | 无命中问题的原有脱敏记录 |
| usage_log | 原有用量日志写入等待（包含失败等待） |
| total | 服务端进入处理函数到响应构造完成，含上述日志等待 |

没有执行的阶段不返回字段。阶段异常仍计时。`total` 还包含解析请求等零散工作，
不要求等于各阶段之和。它不包含进入函数前的网关、实例启动和网络时间。
响应头只有固定阶段名和毫秒数，不增加数据库字段或性能日志，不包含问题、答案或凭据。
成功响应还返回模型接口格式和思考开关状态，基准报告只保存这两个非敏感枚举值，用于证明优化是否真正生效。
旧 `ai_usage.latency_ms` 的计算口径保持不变，仍不含访问校验和末尾用量日志，不能混用。

为了保留可靠起点，本次没有改变执行顺序、模型、检索阈值、缓存、超时或日志策略。

## 真实基线：需要单独授权后执行

真实提问会消费配额、调用计费模型，并写入配额/用量日志；无命中还会写脱敏缺口记录。
必须先部署带计时的函数，核对线上模型、知识版本、地区和代码版本。
部署前记录原线上版本，以便回退。本阶段不调整数据库或放宽权限。

### 1. 固定测试条件

- 固定使用脚本中的 10 道已有检索测试题，涵盖报到、宿舍、补考、资助、实习、校历、公交和食堂。
- 同一次对照使用相同模型、知识版本、网络位置、客户端超时（70 秒）和串行请求方式。
- 原版、优化版都使用带计时的代码，记录各自准确提交或补丁版本；本地未提交代码不能仅标 HEAD。
- 记录测试时间、模型配置、知识快照标识和运行地区；不要把任何密钥放进这些说明字段。
- 同一个测试设备 ID 持续使用，不能通过轮换绕过配额。
- 当前默认每小时 12 次。建议每批 10 题、每题 1 次，等待额度恢复后再测，共三批。
  批次间不要变更模型或知识；遇 429 脚本立即停止。授权测试环境若已有充足额度，可一次每题测 3 次。
- 固定题中出现无命中也必须保留，不能临时替换成更容易命中的题。

### 2. 配置与执行

在仓库根目录 PowerShell 中，通过当前进程环境变量配置以下字段，不把密钥写进仓库：

| 环境变量 | 内容 |
| --- | --- |
| AI_BENCH_ENDPOINT | 已部署的 campus-ai 完整 HTTPS 地址 |
| AI_BENCH_PUBLIC_KEY | 浏览器使用的 publishable/anon key，严禁 Secret/service-role |
| AI_BENCH_CLIENT_ID | 固定测试匿名 ID，8～128 位字母、数字、下划线或连字符 |
| AI_BENCH_REVISION | 部署代码的准确版本 |
| AI_BENCH_MODEL | 模型名称及影响生成的配置说明 |
| AI_BENCH_KNOWLEDGE_VERSION | 测试期间不变的知识快照/版本标识 |
| AI_BENCH_ENVIRONMENT | 测试环境、服务地区与客户端网络说明 |

示例命令（先配置上表，且获得真实测试授权）：

```powershell
New-Item -ItemType Directory -Force out/ai-performance
node scripts/benchmark_campus_ai.mjs --live --repeats 1 --output out/ai-performance/baseline-1.json
```

部署 M6 后使用相同条件增加 `--stream`，报告会额外记录首段文字时间：

```powershell
node scripts/benchmark_campus_ai.mjs --live --stream --repeats 1 --output out/ai-performance/stream-1.json
```

额度恢复后，分别保存 `baseline-2.json` 和 `baseline-3.json`；脚本拒绝覆盖已有报告。
输出目录 `out/` 已被 Git 忽略。报告不保存题目正文、回答正文、凭据或设备 ID。
报告仅保存固定题号、轮次、状态、来源数量、答案长度和耗时；答案质量需另做人工核对。
合并同条件批次，不发送网络请求：

```powershell
node scripts/benchmark_campus_ai.mjs --summarize out/ai-performance/baseline-1.json out/ai-performance/baseline-2.json out/ai-performance/baseline-3.json
```

输出中位数及最近秩法 P95（95% 样本不超过的耗时）。30 个样本的 P95 仅是初步参考。
成功答案、无命中、错误分别统计，避免错误快速返回把结果“变快”。
`headers_ms` 是测试客户端收到响应头时间，`complete_ms` 包括完整正文读取解析；均不含网页绘制。
流式报告中的 `first_text_ms` 是测试客户端收到第一段非空回答文字的时间；`interruption_rate` 是收到 `error` 或未收到 `done` 的比例，`retry_rate` 仅统计报告中明确标记的重试样本。
默认超时覆盖正文读取。这里的 70 秒测试预算比当前网页仅覆盖响应头的预算更严格，报告比较需保持一致。
若报告缺少 `server.total`，应先核查部署；不能声称已经完成瓶颈归因。

### 3. 浏览器体验补测

通过 `node scripts/dev-server.mjs` 启动页面，访问 `http://127.0.0.1:4173/#/ai`。
真实页面提问同样需要授权，会消耗额度。手机和桌面各选相同问题，使用浏览器开发者工具：

1. 在 Performance（性能）面板开始录制并启用截图，点击发送，等答案出现后停止。
2. 从发送点击事件量到截图中首次出现答案文字，以及完整答案显示的时间。
3. 在 Network（网络）面板定位 campus-ai 请求，记录响应头等待、总请求时间与 Server-Timing。
4. 只记录题号、环境和数字，不导出可能包含凭据或问题正文的完整网络记录。

线上函数已支持流式回答；前端发布后应同时记录首段文字与完整显示时间。响应头时间不能称为首字时间。
这些手工数据与脚本结果分别记录，不混合计算。
浏览器耗时减服务端耗时包含网络、网关等多种因素，不能直接解释为冷启动。
首次请求标为“首次观测”，脚本统一记录 `instance_state: unknown`。
只有获得平台侧实例启动证据后才区分冷/热实例；不要用空闲几分钟推断。

## 优化决策与完成标准

有真实基线后，先列出耗时占比与失败原因，再选最小改动：数据库/向量等待占主导时评估并行；
模型占主导时评估上下文与模型；日志占主导时评估有可靠生命周期保障的异步记录。
未经验证不引入知识或答案缓存，避免退审/失效资料继续被使用。

验收需要：同条件前后报告、全部离线测试通过、超时/故障仍能降级、来源与有效期不退步，
并人工核对固定问题的答案事实、完整性和引用。不能只用来源数量或字数代替质量。
根据真实基线再确定具体提速目标。如果修改前端，按 AGENTS.md 补做手机/桌面全页面检查并更新静态版本号。

### 首轮线上候选与修正版

阿里云百炼官方文档说明，`qwen3.5-flash` 属于混合思考模型且默认开启思考；简单任务可传入 `enable_thinking: false`，关闭思考以降低耗时。官方 Responses API 文档说明 Node.js/HTTP 请求也在请求体顶层传入该参数。官方排障说明把长提示词约 50 秒的响应列为思考模式常见表现。参考：[深度思考模型的用法](https://help.aliyun.com/zh/model-studio/deep-thinking)、[Responses API](https://help.aliyun.com/zh/model-studio/qwen-api-via-openai-responses)、[qwen3.5-flash 模型信息](https://help.aliyun.com/zh/model-studio/qwen3-5-flash)。

v24 首轮候选仅对百炼 `qwen3.5-*` 的 Chat Completions 请求默认发送 `enable_thinking: false`，不改变检索、上下文、来源、输出上限或超时。线上 10 题全部成功，完整响应中位数从基线 36.916 秒降到 32.216 秒，下降 12.73%；模型阶段中位数从 35.431 秒降到 30.588 秒。8/10 道题比各自的基线中位数更快，但 P95 只从 56.571 秒降到 55.977 秒，下降 1.05%。平均回答长度从 480 字符降到 450 字符。

v24 响应没有记录实际接口格式和思考状态；生产 Secret 也未读取。因此，如果线上使用 Responses API，v24 的参数就没有生效，上述差异可能只是服务波动，不能据此确认 12.73% 是稳定提速。

v25 修正版已经部署，bundle SHA-256 为 `2d66317f7051263686c6de91f151d30d6acaa84fe9b4d85745100a8f7483b63a`。它同时支持 Responses 和 Chat Completions，并在成功响应及脱敏报告中记录接口格式与思考状态。10/10 个成功样本均在线确认实际使用 `responses` 且思考状态为 `disabled`。

v25 的完整响应中位数为 6.815 秒，P95 为 10.719 秒；相对 v23 基线分别下降 81.54% 和 81.05%。模型阶段中位数从 35.431 秒降至 4.716 秒，下降 86.69%。10/10 道题都比各自的 v23 基线中位数更快，配对变化中位数为 -82.40%。相对 v24，完整响应中位数下降 78.85%，P95 下降 80.85%。10 个成功样本的来源数量均与 v23 和 v24 相同；平均回答长度由 v23 的 480 字符增加到 541 字符，因此提速不是由统一缩短回答造成。

完整成功集通过 12 次实际尝试得到：一次在旧额度窗口用尽后返回 429，脚本按规则停止；一次在新窗口刚开始时出现无服务器计时的网络/解析错误，随后只重试该题并成功。原始记录均保留，没有隐藏失败或轮换匿名标识。成功集报告为 `out/ai-performance/optimized-thinking-off-v25-complete.json`，三版本对比为 `out/ai-performance/comparison-v25.json`。

本次部署不包含数据库迁移或知识写入。最近一次已核验知识指纹仍为 `766e9d187322406aa891e8ede7bd3eb8`（60 篇已发布、59 篇有效），但 v25 测试前没有再次使用高权限凭据查询该指纹，因此报告明确标为“last verified”。10 题来源数量全部一致，只能证明检索数量未变，不能代替答案事实、完整性和引用的人工核对。v25 健康检查响应报告 `us-west-1`，而 v23 基线健康检查曾报告 `ap-northeast-2`；模型阶段的大幅下降与关闭思考一致，但地区差异意味着这不是严格的同地区实验。10 个样本的 P95 也只是初步值。
